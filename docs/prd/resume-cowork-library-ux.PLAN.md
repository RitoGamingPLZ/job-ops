# Ghostwriter in the resume editor

## Review

This review follows the job-resume Co-work chat in source. It covers selecting candidate evidence, reviewing a proposed edit, and saving it. The findings are workflow hypotheses from code inspection. Validate them with a short task walkthrough before changing the layout.

- **A selected source can lose its place.** ResumeCoworkPage sends distinct resume focus and library references. In cowork-ai.ts the bounded catalog admits items already on the resume before explicit references. With a large resume, a chip can name evidence that never reaches the model. A selected project point also needs its parent to fit.
- **The reader has to connect the suggestion to its source.** ResumeEditor.tsx renders operation-specific previews and reasons. A library-backed rewrite needs three pieces together for a decision: the stored fact, the current resume wording, and the proposed wording. Operation names and an Accept button leave the user to infer which version they are keeping.
- **Manual and AI edits take different routes to the same shared record.** The editor exposes reset/save controls for divergent linked content. The page builds a changed-fields patch for manual entry saves. Assistant saves use librarySaveInput and a separate acceptance path. Bulk acceptance already excludes shared writes. Preserve that safeguard and give both routes the same review.
- **One acceptance can finish halfway.** acceptSuggestions.ts can create a library record and then include it in the resume. ResumeCoworkPage saves the resume afterward. On a revision conflict the user sees “Library changes may already be saved.” They need to know which action succeeded and which one to retry.

## Proposed interaction

Someone tailoring a project point opens Ask AI on that line, chooses **Use from candidate library**, searches by project or wording, and picks a source. The composer shows the target line and the selected source under separate labels. The suggestion shows the source with its project, the current line, and the proposed line. **Apply to this resume** keeps the source intact. After applying, the linked line offers **Review library update**. The review shows the stored value, the exact fields that will change and the effect on linked resumes. **Update library item** commits the shared change. Cancel preserves the tailored resume.

For an existing fact missing from the resume, offer **Include on this resume** and preserve its link. For a genuinely new fact supplied by the user, offer **Create library item** with an explicit option to include it on this resume. If creation resolves to an existing record, identify the reused record in the result. Keep contact records out of chat context.

## Implementation sequence

1. **Make evidence selection reliable.** Extend the Co-work composer using the existing reference state and library item IDs. Provide a keyboard-accessible picker alongside the existing drag interaction, with kind, parent and inclusion status. In cowork-ai.ts allocate the bounded catalog to selected evidence and required parents first. If explicit selections alone exceed the budget, identify the omitted selections before generating. Test a selected point late in a large library and a stale selection.
2. **Make proposals reviewable in place.** Extend the existing suggestion renderer with destination-specific actions and field-level before/after values. For rewrites, carry validated source IDs where the current operation lacks them. Resolve labels from the active workspace library. Keep imported evidence, freely drafted text and linked edits distinguishable. Preserve individual dismissal, stale-target checks and resume-only bulk acceptance.
3. **Unify shared saves.** Route manual promotion and assistant promotion through one review component and changed-fields patch builder. Use current library values as the baseline. Show only fields being written, preserving job-specific skill selections and unrelated fields. Check both reviewed resume and library versions at commit, return a conflict if either changed, and reopen the diff with fresh values. Verify propagation for linked copies and local overrides before wording the impact notice.
4. **Make outcomes definitive.** For combined create-and-include, prefer a workspace-scoped server operation committing the library write and revision-guarded resume save in one transaction after confirming repository transaction support. Otherwise persist per-step results and retry only the unfinished resume step using the returned library ID. Cover deduplication, double submission, revision conflicts and a lost response. Show the saved destinations and a recovery action at the affected suggestion.
5. **Validate the experience.** Walk through three tasks with a populated library: use an older project point, tailor a linked line for one job, and correct a shared fact. Before each commit ask the participant which records will change. Ship when they can predict the destination, recognize the source, and recover from a conflict without duplicate records. Test keyboard operation, empty libraries, legacy unlinked content, cross-workspace IDs and base-resume behavior. Update the user-facing feature docs and run all five repository CI-parity checks on the implementation.

Deliver the picker and resume-only proposal review as the first slice. Shared promotion follows once exact patches, propagation and conflict handling are covered together.
